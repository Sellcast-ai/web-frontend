# Lumi Web

Next.js 16 (App Router) frontend for Lumi - turns product listings into shoppable videos.
No custom domain is attached yet; the site is served from its Vercel deployment URL, and every place that needs the site's own origin reads it from `src/lib/site-url.ts` (never hardcode a hostname).
The browser never talks to the backend directly; all data flows through the BFF routes under `/api/bff/*`, which proxy to the Sellcast FastAPI backend (separate repo/dir: `../backend`, dev default `http://127.0.0.1:8000/api/v1`).

## Commands

- `npm run dev` - dev server (npm; `package-lock.json` is the lockfile)
- `npm run build` / `npm run start`
- `npm run lint` - ESLint 9 flat config (`eslint.config.mjs`, eslint-config-next)
- `npm run test` - vitest (config in `vitest.config.ts`, tests co-located as `*.test.ts`)
- No formatter script.

## Stack

- Next.js 16.2.6, React 19, TypeScript, Tailwind CSS v4 (via `@tailwindcss/postcss`, theme in `src/app/globals.css`)
- TanStack Query v5 for client state (provider in `src/components/providers.tsx`; query keys in `src/lib/api/hooks.ts` as `qk`)
- `class-variance-authority` + `clsx` + `tailwind-merge` (`cn()` in `src/lib/utils.ts`), lucide-react icons
- framer-motion (`motion` package, imported from `motion/react`) for animation; shared primitives/tokens in `src/components/ui/motion.tsx`, app-wide `<MotionConfig reducedMotion="user">` in `providers.tsx` (plus a `prefers-reduced-motion` guard for CSS keyframes in `globals.css`)
- Path alias `@/*` -> `src/*`

## Structure

- `src/app/(marketing)/` - public pages (landing, pricing, features, legal, blog...)
- `src/app/(auth)/` - login/signup (phone OTP + Google OAuth), visitors only: both pages call `redirectIfAuthenticated` (`src/lib/auth-redirect.ts`), so an authenticated user can never land on `/signup` from any CTA. Phone is not a guaranteed path: when `send-code` answers with the `development` delivery channel or fails as SMS-unconfigured (both in `src/lib/phone-auth.ts`), the form latches into an unavailable state and points at Google instead.
- `src/app/app/` - authenticated product app (products, connections, studio, videos, jobs, avatars, profile). Marketplace is deliberately off the launch surface: the route is deleted and a temporary `redirects()` entry in `next.config.ts` sends `/app/marketplace/:path*` to `/app/products` so old bookmarks keep working; `src/lib/launch-routes.ts` owns the shared entry hrefs (`APP_HOME_HREF` is `/app/products`) and documents the restore path. Only the web surface is hidden - the backend marketplace endpoints stay reachable through the generic BFF proxy, and marketplace-sourced product rows (no `owner_user_id`) still exist, so the product detail page keeps its commission/sales-analytics blocks behind that check. `app/layout.tsx` redirects to `/login` when session cookies are absent (no middleware.ts), and sets the `Studio` title default + `TITLE_TEMPLATE`; each route owns a thin `layout.tsx` whose `generateMetadata` pulls its title from the catalog (page files are client components, so they can't export metadata themselves). A segment that declares `title.default` drops the inherited template for its children, so `products/layout.tsx` re-declares `TITLE_TEMPLATE` to keep `products/new` and `products/[id]` suffixed. My Products has three mutually exclusive states below its paste box, all keyed on whether a list has ever arrived (`data !== undefined`, never `isLoading`, which is false for a query paused offline): a fetch that never landed renders its own error card with a retry (never the empty state - a broken fetch must not read as "no products"), an empty catalog renders one empty state whose primary action is importing the whole store, and a near-empty one (1-3 products) keeps the store-import prompt above the grid. A refetch that fails *over* cached products is a toast instead, so the error copy never sits above the grid it claims failed to load. Offline is the same dead end as a failed load - React Query pauses the query, so there is neither data nor an error - and gets that same card with its own copy and the retry disabled ("Waiting for connection"), because the default `networkMode: "online"` makes the click inert and the query resumes itself on reconnect. That card's failure branch and the import card's "stop tracking" exit are both gated on `errorUpdateCount > 0` rather than `isError`, which a retry over no data resets to false and which would blink the recovery UI away mid-retry. All of them link to the existing `/app/products/new` store-import flow. Icon-tile headers on this page and the add-product page all render through `components/app/path-header.tsx`.
- `src/app/app/connections/` - the Stores page (sidebar "Stores"). The platform grid is data-driven (`PLATFORMS` in the page): adding a platform is a data entry + catalog keys (`app.connections.platforms.<id>.*`), not a rewrite. Honesty rule baked in: a card may only offer connect when that platform works end to end - only Shopify does, and even its card is gated on a runtime availability probe (`useShopifyAvailability` -> `auth/shopify/status`), so it shows "unavailable" instead of a failing button whenever the deployed backend lacks the route or the OAuth config. **The backend has no list/disconnect endpoints yet** (only `connections/shopify/start|callback`), so the "Your stores" section is an honest placeholder, not a list - revisit when the backend lands them (`PlatformConnection` in `types.ts` already mirrors `PlatformConnectionResponse`).
- `src/app/api/bff/` - BFF route handlers:
  - `[...path]/route.ts` - generic authenticated proxy (`maxDuration = 180` for slow Apify product parses and the store catalog walk)
  - `auth/google`, `auth/phone/send-code`, `auth/phone/verify`, `auth/logout` - set/clear session cookies
  - `auth/shopify/start`, `auth/shopify/callback` - the Shopify OAuth round trip, browser-navigated (not fetch): `start` forwards the backend's 302 to Shopify plus its HMAC state cookie (which must land on *this* origin, because the backend's `redirect_uri` points back at our callback), `callback` forwards query + state cookie to the backend and turns the outcome into a redirect to `/app/connections?connected=<shop>` / `?error=<code>` (never renders backend JSON into a top-level navigation). Both use `callBackendAuthed` in `server.ts` (refresh-on-401, like `proxy`, but lets the route inspect redirects). `auth/shopify/status` is the availability probe: it calls the backend start route with a syntactically valid dummy shop and reads only the status (302 = deployed + configured). The state cookie name is a backend literal (`sellcast_shopify_oauth_state` in backend `app/services/shopify/oauth.py`) - keep in sync like `phone-auth.ts`.
- `src/lib/api/` - the API layer:
  - `config.ts` - server-only config: `SELLCAST_API_BASE`, cookie names (`lumi_at`/`lumi_rt`)
  - `server.ts` - server-only (`import "server-only"`): `callBackend`, `proxy` with automatic refresh-token retry on 401, cookie set/clear. Its own no-cookie 401 body is machine-readable only (`error_type`, no `detail`/`error`/`message`), because any human-looking string there would be treated as the server's message and rendered untranslated
  - `client.ts` - browser `api` object hitting `/api/bff/*`, throws `ApiError`. Both transports (fetch and XHR) build that error in one place, so every failure carries the backend's `error_type` (match on it, never on prose) and its `serverMessage` - the message the *body* carried, which is the only part `apiErrorMessage` will show, kept apart from `ApiError.message`'s client-side English generics ("Bad Gateway", a malformed-JSON 2xx, a dead socket). `bffUpload` is an XHR-based POST used by product/avatar creation to report real upload progress (fetch can't). `uploadReferenceVideo` instead presigns via the BFF (`ReferencePresign`) then PUTs the bytes straight to storage (`putFileWithProgress`), bypassing the app server so large clips dodge serverless body limits, and returns the `public_url` to send as `reference_url`
  - `hooks.ts` - React Query hooks wrapping `client.ts`
  - `types.ts` - shared API types mirroring backend schemas
- `src/lib/toast.ts` - framework-free toast store (`toast.success/error/info` from any event handler or mutation callback); rendered by `ui/toaster.tsx`, mounted app-wide in `providers.tsx`
- `src/lib/use-dropzone.ts` - shared drag-and-drop hook (spread `props` on the drop target, style via `over`)
- `src/lib/subjects.ts` - pure helper for the storyboard locked-subjects strip (`orderedSubjects` sorts Product -> Host -> Scene and omits when empty; `SUBJECT_HEADING_KEYS` maps kind to catalog key)
- `src/lib/job-progress.ts` - pure helper for the job-detail progress tracker (`STEP_LABEL_KEYS` + `stepIndex` map `job.status` to a stage; storyboard-present on a queued/submitted job means the review gate is behind us, so it shows Render, never backtracking to Script/Beats)
- `src/lib/phone-auth.ts` - `isDevDeliveryChannel` / `DEV_DELIVERY_CHANNEL`, the single place that knows the backend's `development` SMS provider literal (`PhoneDeliveryChannel` in `types.ts`); keep it in sync with backend `app/services/sms.py` rather than string-matching the channel at call sites. Also owns `isSmsUnavailableError`, the "phone can't work on this deployment" predicate for a failed `send-code`: it matches `SMS_NOT_CONFIGURED_ERROR_TYPE` (the structured `error_type` the backend returns as 503, carried on `ApiError.errorType`) *or* any 503 from that call, because `error_type` is derived from a backend Python class name and a rename there must not silently unlatch the final state. Never key on message prose
- `src/lib/auth-redirect.ts` - server-only session-cookie presence check (`hasSession`), the one session predicate for server components (presence only; the BFF proxy owns validity/refresh) - used by the marketing layout and the app-shell layout's `/login` redirect - plus `redirectIfAuthenticated` for the auth pages
- `src/lib/contact.ts` - `BILLING_EMAIL`, the one billing inbox the site advertises while checkout isn't self-serve (pricing upgrade dialog + FAQ, refunds page); the catalogs interpolate it as `{address}` so no locale can be left naming a dead address
- `src/lib/import-selection.ts` - pure helpers for the store-import review step (sessionStorage persistence of the *deselected* set, `selectedUrls`, and `importOutcome`, which derives the finished-import toast from the counters rather than `job.status`, so a partial never reads as a clean success and a run that landed products nobody picked reads as a warning rather than a green success). The review step's shape is a settled product decision, not an accident of the diff: every candidate starts selected, one click deselects all, a live "N of M selected" count (`aria-live="polite"`) sits above the list, only the selected products are submitted for import (see the backend gap below), and the list renders every candidate - no client page cap, no virtualization - so select-all/deselect-all can never mean "just the ones on this page". The store flow is preview -> review -> commit: `POST products/import/candidates` lists the catalog, and `POST products/import` carries `source_urls` (the reviewed subset).
The add-product start screen gives store import its own first section, keeps the single-product URL parse form separate, and has exactly one manual editor entry - a drop target holding two explicit buttons (open the blank editor, or start with photos via the file picker), so nothing on it promises a file dialog a click doesn't open, and dropping photos on it still opens the editor with those photos attached.
While a store flow owns that screen (catalog walk, review or running import) the single-product and manual sections are suppressed, so no adjacent click can unmount a review mid-pass.
That flag is split along ownership: `StoreImport` reports only its own half up through `onReviewingChange` (`review !== null`), the running-import half lives on the page in `useImportSlot`, and the page computes `storeFlowActive` from the two.
Leaving is deliberate, through the flow's own exit - "Try a different store" on the walk and review steps, and "Add something else while this runs" on the progress card, so a slow or stuck job never leaves the page without a usable control (it drops the live progress card only; the import itself carries on server-side, exactly as a reload does). A pass that does get unmounted is not lost: it lives in sessionStorage and `beginSelection` carries it back into the next review of the same store.
**The backend does not accept `source_urls` yet.** The field is not in the import schema at all, so pydantic drops it silently and the worker imports the whole catalog regardless - measured against the real backend, 136 selected, 139 imported. The selection is therefore *advisory* until the backend half lands, and the two halves have to merge together for this feature to mean anything. Keep sending `source_urls` (and `platform`): it is the contract the backend lane is being written against, not a leftover.
Four pending requirements on the backend, which the web side is written to: (1) `products/import/candidates` has to exist - the web side ships first, so a live store import 404s on candidates until it does; (2) `POST products/import` has to honour `source_urls` and import only that subset, so the client's `requested` - the length of the `source_urls` it sent, never `products_found`, which legitimately counts the whole catalog the walk touched - matches what lands; until it does, a run that lands more than was chosen surfaces as `importOvershoot` / `importIgnoredSelection` rather than being hidden, which is exactly what the measurement above trips; (3) `candidates` has to return a `platform` drawn from the import adapter registry (currently `shopify` | `woocommerce`), because the client forwards it verbatim as the import's `platform` and `adapter_for()` raises -> 422 on anything outside that registry; (4) `candidates`' own page cap has to be `>=` the import worker's cap: the review step is now the only way in, so anything the walk doesn't list can't be imported at all, and "select all" has to still mean everything the old whole-catalog import would have taken.
On the client side the progress bar and the finished-import toast both quote its own count of the chosen subset, that one value and never two derivations of it, and the review step never re-enters the (billed) catalog walk without a click. `src/lib/import-selection.test.ts` covers client behaviour only - which subset is computed, persisted and reported - and is not evidence of the end-to-end outcome.
The *only* thing persisted is the deselection pass, keyed by the current user id and the normalized `store_domain` it was made against (never the raw pasted string - `shop.example.com` and `https://shop.example.com` are the same store, and so is the catalog cache key `qk.importCandidates`, or the second spelling buys a second billed walk). It is read at the point of use (`beginSelection`, inside `reviewStore`, on the click), never at mount.
The one mechanism protecting a pass from the wrong reader is the `parsed.userId !== userId` discard inside `loadSelection` - it covers logout, an expired session, and every exit nobody enumerated, so don't add `clearSelection()` call sites back to the exits and don't delete that check believing some other guard covers it.
What protects a pass from its own writer is that **only a deliberate selection gesture writes it** - a row toggle, Select all, Deselect all, all of them through `applySelection`. Entering a review, restoring one, and every mount/render path are read-only, so it no longer matters *why* a read came back empty: it has no way to overwrite what's stored. (Three separate bugs - an unresolved user id, a too-narrow write guard, a key mismatch - were all one restore path being allowed to write.) For the same reason the two exits differ: `discardReview` (from a review the user has seen) drops the stored pass, `leaveWalk` (backing out of a catalog walk that never landed) leaves it alone.
Deleting is scoped the same way writing is: `clearSelection` takes the store identity it is leaving and removes nothing else, so discarding a review of store B can't take the pass the user made for store A.
Storage is one slot on purpose: it holds one pass, for one store; incidental operations (leaving a card, finishing an import) never touch another store's pass; a deliberate selection gesture in a new store takes the slot. The requirement was that a reload mid-review doesn't cost the user their pass, which one slot covers - keeping several stores alive at once means a map plus an eviction policy, and that is not a bug to re-litigate.
This feature also attracted dead defensive branches - a `keepJob` flag, `resumeFor`'s `domain` return, two unreachable `??` fallbacks, an unresolved-user guard that `AppShell`'s session spinner made impossible, an `importRequested` helper that had shrunk to an identity function - all of them defending states the feature's own cuts had already made impossible, and all removed rather than documented. Prefer deleting an unreachable branch here over commenting it.
Two things were deliberately *not* kept, both because they guard invariants the server already holds and both of which produced a long tail of stale-restore bugs: a client-side pre-flight duplicate-import marker, and a persisted job handle (with a resume banner and dead-handle recovery around it). `POST products/import` returns the caller's existing active job instead of enqueueing a second, so a reload-then-click can't buy the same import twice - a reload mid-import just loses the live progress card and shows the paste form, which the "keeps going in the background" copy already covers. Don't re-add either.
What a running import *does* keep is component-lifetime state, and it lives in `useImportSlot` on the page rather than inside `StoreImport`: opening the manual editor unmounts `StoreImport`, so a guard held there would forget the running job on the way back and offer a second import the backend would answer with that very job (re-labelling it as the new store's, and clearing a pass for a store nothing imported).
While that job is in flight the store path shows the already-importing card instead of the paste form - an action that can't be performed correctly isn't offered.
The counterpart invariant: a terminal job *must* release the `running` handle, because `storeFlowActive` is computed from it and a job that fell through renders no card at all - so an early `return` added to the finish effect that skips `setRunning(null)` (exactly the shape of the `failed` and `importNone` branches) strands the page with the single-product and manual sections hidden and nothing in their place.
A handle the page can never read - the job GET failing for good - is the one case nothing can infer, so the unknown-job card carries its own "stop tracking" exit; it drops this page's handle only, and says so, since the import keeps running server-side.
The catalog walk (`useImportCandidates`) is billed, so every automatic trigger is off - no retry, no refetch-on-reconnect - and it may only ever start from a click (`reviewStore`, or the "Try again" button, which reads `isFetching` so a walk in flight can't be clicked a second time).
Anything changed here has to answer three questions, because this change's real bugs were found in them: what happens on a **reload**, what happens when **`StoreImport` unmounts and comes back** (the manual editor does exactly that), and what happens when the **next account signs in in the same tab**.
- `src/lib/metadata.ts` - `TITLE_TEMPLATE` (`%s · Lumi Studio`) shared by the app-shell layouts; the marketing/root template stays `%s · Lumi` in `src/app/layout.tsx`
- `src/lib/menu-placement.ts` - pure helper picking which side a popover opens on and its `maxHeight` from the trigger rect + viewport (never below `MIN_MENU_HEIGHT`), so tall menus scroll instead of spilling past the fold
- `src/lib/vibe.ts` - `defaultStyleForMode` derives the (now non-user-facing) `style` from mode. Vibe (`VIDEO_VIBES` in `types.ts`) is the hero creation control in Studio; style demotion is a locked product decision - keep sending a valid `style` in the create payload so the backend schema stays intact. Studio also has an optional "Make it like this" reference input with two tabs - paste a supported social link, or upload a clip (`api.uploadReferenceVideo` presigns + streams direct to storage) - that adds `reference_url` to the create payload only when a valid link is entered or an upload completes; Generate is gated while an upload is in flight or the link is invalid. It's additive, so no reference means the body is unchanged; the seller-facing framing is that Lumi learns vibe/energy only, never the reference's shots.
- Shot edit drawer (`ShotEditor` in `src/app/app/jobs/[id]/page.tsx`) is plain-language first: spoken line, on-screen text, the `OUTCOME_NUDGES` taps (`Shot.outcome_nudges`) and a free-text `nudge_note`; raw camera fields (`technique`/`transition_out`/`product_visible`) hide behind the "Pro mode" disclosure. The backend derives the camera fields from the taps/note (deterministic map + single-shot GPT re-derive, all via the existing `PATCH /storyboard` sending the full `VideoScript`), so the `OutcomeNudge` value strings are canonical English the backend keys on exactly - don't reword them, and don't leak camera jargon onto the main read-first path (the shot card hint shows applied taps/note, not `technique`).
- `src/components/` - `ui/` (button, badge, motion primitives, `overlay.tsx` Modal/Drawer on native `<dialog>`, toaster, upload-progress), `app/`, `auth/`, `marketing/`, theme provider/toggle

## i18n (UI language)

App-interface localization uses **next-intl v4**, cookie-based (no `[locale]` URL segment yet). Config in `src/i18n/request.ts` (`getRequestConfig` reads the `lumi-locale` cookie, default `en`; v4 requires returning `locale`), wired via `createNextIntlPlugin` in `next.config.ts`. Root `layout.tsx` is async: `getLocale()` sets `<html lang>` and `NextIntlClientProvider` (prop-less, inherits messages) wraps the client tree.

- Catalogs: `messages/<locale>.json` at repo root, `en.json` is the source of truth. All 9 UI catalogs (`en, es, zh, ja, ko, pt, id, vi, th`) mirror the same key/placeholder structure; `src/i18n/messages.test.ts` enforces parity. The 8 non-English catalogs are an AI-translated seed regenerated from `en.json` via `node scripts/translate-messages.mjs [locale...]` (protects brand names, ICU/simple placeholders, and rich-text tags; `MANUAL_OVERRIDES` in that script pins strings the machine gets wrong) - re-run after editing `en.json` keys, then refine by hand. Exception: `marketing.landing` (+ footer tagline) was hand-translated in all 8 locales (July 2026, landing rebuild), as was `marketing.features.rows` (July 2026, claims cleanup - the machine had read the `publish.kicker` verb "Ship" as the noun and shipped "boat" in every locale) - patch those keys surgically rather than regenerating the whole catalog, which would clobber them with machine output. `shared.theme.*` is pinned in `MANUAL_OVERRIDES` because the machine reads "Light"/"Dark" as brightness rather than a UI colour scheme ("Luz", "光", "빛", "Ringan"), and now that the toggle is on the marketing header those labels are the aria-labels every visitor's screen reader reads.
- For enum/data label maps, translate at the render site: pure `lib/*` helpers expose stable catalog keys (for example `STEP_LABEL_KEYS`, `SUBJECT_HEADING_KEYS`, or `SOURCE_LABEL_KEYS` in `app/product-card.tsx`) and components call `t(key)`. Do not import next-intl hooks into `lib/*` or `hooks.ts`. Mutation hooks in `hooks.ts` that show toasts take a `messages` object of already-translated fallback strings (under `app.toasts.*`) supplied by the calling render component, so `hooks.ts` never touches the catalog itself.
- Switcher: `src/components/language-switcher.tsx` (globe dropdown, writes `lumi-locale` cookie + `router.refresh()`), mounted in the marketing `SiteHeader` (`compactOnSmall` drops the label below `sm`, keeping the aria-label) and beside `ThemeToggle` in both the marketing header and `AppShell`. Menu direction/height are measured at open and on resize/scroll via `lib/menu-placement.ts`, so it always scrolls inside the viewport instead of clipping a locale - never wrap it in an `overflow-hidden` container or hardcode its height. Lists and enables all 9 target locales by endonym. This UI-language enablement is independent from `VIDEO_LANGUAGES` (the video-output axis, whose availability is backend/voice-QA controlled).
- **Separate from video-output language**: never route `VIDEO_LANGUAGES` labels through the catalog, and never wire the UI locale into the video-create `language` payload. The landing "reach" card renders the enabled `VIDEO_LANGUAGES` labels straight from `types.ts` for the same reason, but the count around it is prose (`landing.why.reach.body`/`.caption`, `landing.marquee.languages` all say eight/8) - flipping an `enabled` flag means editing those strings in all 9 catalogs. See the i18n plan (PR sequence PR-1..PR-R) for remaining migration.
- Reading the cookie at the root layout makes marketing pages render dynamically; static + `hreflang` SEO is restored later by the `[locale]` prefix PR (PR-R).

## Marketing vs app styling (split posture)

The marketing surface and the logged-in app deliberately diverge (UI-sophistication PR series V1..V7).
The marketing layout wraps its tree in a `.marketing` class (`src/app/(marketing)/layout.tsx`); the scoped block in `globals.css` overrides `--font-display` to the editorial grotesk (Geist), defines `--font-accent` (Instrument Serif italic) + tighter tracking, and narrows `.container-page` to 64rem there only (the app keeps its wider 76rem).
The app never enters `.marketing`, so it keeps the SF-Rounded/Nunito cream system untouched - keep any editorial type/palette-restraint treatment scoped to `.marketing`, never at `:root` or in `app/*`.
Serif accent phrases in marketing headings use `<Accent>` (`src/components/marketing/accent.tsx`), one phrase per major heading (the `<highlight>` tag in catalog strings).
Marketing palette is monochrome + one accent (the teal `brand` ramp for CTAs; green means live/approved only - `--color-live` on the fixed-dark panels); do not reintroduce decorative rose/gold/orange or gradient headline text.
The landing (V4+V5) is banded: light hero with the simulated-pipeline stage (`marketing/pipeline-hero.tsx`, a client state machine replaying link -> pattern -> storyboard approval -> render while in view; static finished state under reduced motion), capability chip marquee, dark fake-UI media cards, one dark inset story panel, output wall, pricing, FAQ, dark CTA panel with ghost wordmark.
Marketing carries the theme toggle too (captain's call 2026-07-29, reversing the earlier app-only choice), so the "light" bands are the `:root`/`.dark` tokens and flip with it, while the "dark" ones are literal hex gradients + `text-white/*` and stay dark in both themes - that alternation is the page's contrast rhythm, not a dark-mode bug, so don't tokenize those panels to make them lighten.
Showcase footage is wired through `marketing/showcase.ts` (`HERO_OUTPUT_VIDEO`, `OUTPUT_WALL_VIDEOS`) and played by `marketing/showcase-video.tsx` (the poster loads as the slot nears the viewport - the hero's is the page's one eager fetch - clip bytes only near the viewport, still under reduced motion); an unfilled slot renders the section's closing statement card instead of a video.
Those slots hold real Lumi renders (provenance in `docs/marketing-showcase-sources.md`, deliberately outside the publicly served `public/` tree), so the page carries no stock-footage disclaimer; if a slot ever falls back to stock, that copy comes back with it - never let stock read as Lumi output, or Lumi output read as stock.
`HERO_OUTPUT_VIDEO` and five of six wall tiles are filled; `fitness` is `null` because the only two candidate renders carry someone else's marketing burned in (a discount price splash, a third-party store URL), and an unfilled slot renders the section's closing statement card rather than a labelled empty gradient.
Judge a candidate render by watching it, not by its filename or a single frame - the reject table in `docs/marketing-showcase-sources.md` exists because burned-in store watermarks and hard-sell overlays are only visible in the footage itself.
The clips carry voice, so `showcase-video.tsx` plays them muted behind a corner sound toggle that is client-only (hydration-safe) and module-scoped, so unmuting one clip mutes any other.
The toggle sits dimmed until the slot is hovered or the button focused (never dimmed on touch devices or while loud) - that recede is deliberate, not a contrast bug.
`next.config.ts` long-caches `/marketing/videos/*`: files under `public/` default to `max-age=0`, which made every return visit re-download the whole wall.
The marketing header is deliberately slim (logo, Pricing, language switcher, theme toggle, Sign in, one CTA; server component, no menu state); below `sm` the Pricing and Sign in links drop out and the logo collapses to its mark so the row can't overflow at 320px, leaving mark + switcher + theme toggle + CTA (both links stay reachable from the footer, which carries its own sign-in link for signed-out visitors).
The CTA is the one item that may never drop, so below `sm` the signed-out one swaps to a shorter label of its own (`marketing.header.startFreeMobile`, pinned per locale in `MANUAL_OVERRIDES` and keeping the desktop "Start" verb rather than a literal truncation) - that plus the shaved row widths is what buys real 320px headroom in all 9 locales, so keep both spans if you touch it.
The whole marketing surface is auth-aware, from one place: the layout resolves `hasSession` once and publishes it through `MarketingSessionProvider` (`marketing/auth-cta.tsx`), and every body CTA - `CtaBand`, the landing hero, the landing pricing-footer link, the landing final CTA, the blog CTA - renders `AuthCta`/`AuthCtaLink`, which point a signed-in visitor at `APP_HOME_HREF` under `marketing.header.openStudio` instead of `/signup`.
Add a CTA through that primitive, never a bare `href="/signup"`; the header and footer are server components that can't read the client context, so the layout passes them the same already-resolved boolean as a `signedIn` prop (one `hasSession()` per request) and they swap the same way.
Pricing swaps too (`PricingClient` reads the same context): Free's CTA becomes "Open Studio" and the paid tiers open a "billing isn't self-serve yet" dialog (mailto `BILLING_EMAIL` from `src/lib/contact.ts`, which the catalogs interpolate as `{address}` so the inbox is one edit) because there is no checkout/billing route in the frontend or backend - do not point authenticated users at `/signup?plan=` again, and do not invent a checkout.
The pricing FAQ answers the same way (`marketing.pricing.faq.a3`/`.a4` name the email path in all 9 catalogs); a claim that upgrades "apply immediately" contradicts the dialog on the same page, so keep the two in sync.
`/pricing` is the *only* surface that decides what a *paid* click does, so it owns that decision alone: the landing page's paid-tier cards link to `/pricing` under one shared marketing-namespace label (`marketing.landing.seePlans` - never reuse `app.studio.seePlans`, whose translations are written for the in-app quota nudge), and no `?plan=` param survives anywhere (nothing consumed it).

## Claims the marketing copy must not make

Marketing copy may only promise what production actually renders.
Two capabilities are built but off, so every claim about them was stripped from all nine catalogs (July 2026) - do not reintroduce them without checking the backend first:

- **Burned-in captions.** The backend's `burn_captions` setting defaults to false, its env var is unset in production, and `video_generation.py` returns early from the caption encode when it is false (the encode was OOM-ing the worker). The rendered video does carry spoken voice - that claim is true and stays; only the on-screen caption claim is false. Studio's shot cards still preview `on_screen_text`, which is a storyboard aid, not what ships.
- **AI Avatar mode.** The `ai_avatar` mode, avatar library, and `avatar_*` styles are still in the app and the API, but the mode does not currently produce a working render, so marketing describes product-only output.
  For the same reason Studio's default `mode` is `product_only` (it was `ai_avatar`) - a first attempt must not land on a mode that cannot render; move the default back when avatar mode ships.

To restore the copy when either ships, `git log -S "burned-in captions" -- messages/` finds the removed strings: the landing marquee chips (`landing.marquee.avatar`/`.captions`), `landing.wallSubtitle`, `landing.storySteps.render.body`, `landing.why.reach.*`, `landing.pipeline.caption`, the `pricing.included` / `pricing.tiers.creator.features` / `landing.pricingTiers.creator.features` rows, `faq.a2`, the `features.rows.modes` + `features.rows.publish` blocks, `models.cards.seedance`, and `metadata.features.description`.
Restoring the caption claim also means putting back the caption overlay in `marketing/pipeline-hero.tsx`; restoring the avatar claim means putting back the avatar/product-only mode-toggle pills above the landing reach card's language chips (`landing.why.reach.uiAvatar`/`.uiProductOnly`).
Both need the `UserSquare2`/`Captions` icons back in the two pages' import lists (the features `modes` row now uses `Package`).
Some committed showcase clips still visibly carry burned-in captions because they were rendered while the encode was on - that is deliberate.
They are evidence the capability exists; what was removed is the promise that every render ships with it, so do not swap or re-poster a slot to hide it.
The hero used to be one of them (a presenter to camera, captioned), which asserted both off-capabilities in the page's most prominent frame; it is now a product-only render with no caption, and the captioned clip moved down to the `fashion` tile.
That removes the contradiction at hero scale - it does not un-hedge anything, because neither capability shipped.

## Brand & share metadata

Icons and share cards are file-convention based, so there is no hand-written `<link rel="icon">` anywhere.
`src/app/favicon.ico` + `src/app/apple-icon.png` (opaque full-bleed square - iOS applies its own rounded mask and composites any transparency onto black) are picked up by Next; the 512px `public/icon.png` and `public/icon-maskable.png` deliberately live in `public/` and are referenced only from `src/app/manifest.ts`, because an `icon.png` in `src/app/` would emit a second `<link rel="icon">` competing with the favicon.
`public/lumi-mark.svg` is the vector source the raster icons were exported from - it is not loaded at runtime; re-export the PNGs from it when the mark changes.
`src/app/opengraph-image.tsx` renders the 1200x630 card with `next/og` (its inline mark must keep matching `bg-brand-gradient`); it serves Twitter/X too, so do not add a separate `twitter-image` route.
The teal gradients in `globals.css` (`bg-hero`, `bg-brand-gradient`) carry white text on the surfaces that use them (avatar initials, step badges, dark panels) - both stops must stay dark enough for 4.5:1, so do not brighten the end stop back toward the iOS aqua.

## Auth model

JWTs from the FastAPI backend are stored as httpOnly cookies (`lumi_at` access ~30m, `lumi_rt` refresh ~30d) by the BFF auth routes; tokens never reach client JS.
The catch-all proxy transparently refreshes on 401 and re-issues cookies, clearing them if refresh fails.
Google is the only path guaranteed to work in every environment: `send-code` returning `delivery_channel: "development"` means the backend only logs codes, so `AuthForm` latches the phone step into a disabled "Phone unavailable" state (`auth.phoneUnavailable*` catalog keys) instead of advancing to code entry. The same latch happens when `send-code` fails with the structured `error_type: "SmsNotConfiguredError"` (503, SMS unconfigured in production) - that failure is non-destructive (the phone field keeps its value) and clearly final, not retryable.
That check is post-submit - availability is only known from the first send response, so the user spends one attempt before seeing it; a pre-flight availability endpoint would remove that.

## Environment

## Conventions

- Never import `src/lib/api/config.ts` or `server.ts` into client components (server-only).
- Add new backend calls to `src/lib/api/client.ts` + a hook in `hooks.ts`; the generic BFF proxy means most endpoints need no new route handler (only auth flows that touch cookies do).
- Keep types in `src/lib/api/types.ts` in sync with backend Pydantic schemas.
- Never render `ApiError.message` to a user: it may be a client-side English generic (a status phrase, a parse failure, a dead socket) that would ship untranslated to all nine locales. Show failures via `apiErrorMessage(err, localizedFallback)`, which displays only a message the response body itself carried.
- Reuse the shared UI primitives instead of one-offs: mutations surface success/failure via `toast.*`, overlays go through `Modal`/`Drawer` in `ui/overlay.tsx`, animations use the tokens/primitives in `ui/motion.tsx`.
